# v5 — HPC-style specialization and kernel fusion

Eliminate runtime generality: compile a binary specialized for a specific
(model, machine, quant) triple. Use Nim's compile-time constants and templates
for automatic kernel fusion per layer kind.

## Design

### Static configs

Two structured compile-time configs (see `wmma-experiment-and-specialized-backend.md`
Part 4 for full type definitions):

- **MachineConfig** — hostname, processor, GPU spec (arch, CU count, warp size,
  LDS, VRAM, bandwidth, clock), memory spec (kind, bandwidth, capacity, L2).
  One const per machine (Azem, HighSteel).
- **Model configs** — typed per architecture: `TransformerConfig`, `SsmConfig`,
  `MoeConfig`, `HybridGdnMoeConfig`. Each carries only the fields that apply.
  No loose bag of consts.

Selection via `-d:targetMachine=azem -d:targetModel=qwen36_35b_q4k`.

### What static configs enable

- Loop bounds are literals — compiler unrolls and constant-folds
- No `case layerKind` dispatch — layer sequence is a compile-time straight line
- Dead code elimination — only the target quant format's kernels are compiled
- Machine-aware tuning — block sizes and warp counts from `Machine.gpu.*`
- GGUF loader becomes a weight reader — asserts dimensions match, no discovery

## Tasks

### Persistent mega-kernel per layer kind
- Fused template per layer kind (attnFfn, attnMoe, gdnMoe, ssm, etc.)
- Grid-level barriers (`hippoGridSync` via cooperative launch) replace launches
- Persistent LDS state (input vector stays in LDS across phases)
- Software pipelining: prefetch next layer's weights during current layer
- Requires adding `hippoCooperativeLaunch` and `hippoGridSync` to hippo

### Keep MoE and Delta Net as separate phases
- MoE routing is data-dependent (which expert weights to load depends on router)
- Delta Net recurrence is sequential per-head with error correction
- These don't fuse well into persistent kernels — use inter-phase barriers

### Template-per-layer-kind fusion
- `template attnFfnDecode(cfg: static TransformerConfig, machine: static MachineConfig)`
- Composes rmsnorm+GEMV, GEMV+residual, rope+storeKV with static dimensions
- Compiler inlines and fuses through dead code elimination, no DSL needed

### Type-safe kernel composition
- `GpuTensor[Q: static QuantType, Rows, Cols: static int]` carries quant format
  and dimensions at compile time
- Compile-time errors if quant types don't match what a fused kernel supports

### Incremental path
1. Wire up MachineConfig and one model config as compile-time constants
2. Convert one kernel (e.g. RMSnorm) to use static params, verify output
3. Add grid sync + cooperative launch to hippo
4. Write fused template for one layer kind (attnFfn), benchmark
5. Expand to remaining layer kinds

## Theoretical ceiling

TinyLlama Q2_K pure weight bandwidth: ~400MB at 960 GB/s = ~2400 tok/s.
Actual ceiling is lower (attention reads KV cache, irreducible compute) but
shows the gap between current 371 tok/s and hardware limits.

## Why Nim

- `const` object literals are fully compile-time — structured configs, not
  preprocessor defines
- `template` and `when` give natural kernel specialization without a DSL
- Type system enforces quant format compatibility at compile time
- Dead code elimination and inlining handle fusion that would require a
  code generator in C++/CUDA
- Result: HPC-style specialization with the ergonomics of a high-level language
