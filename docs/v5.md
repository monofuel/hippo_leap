# v5 — Persistent mega-kernel and Nim macro fusion

The endgame optimization: eliminate kernel launch overhead entirely and use
Nim's compile-time metaprogramming for automatic kernel fusion.

## Tasks

### Persistent mega-kernel
- Single kernel launch per decode step that stays resident on all CUs
- Grid-level barriers (`hippoGridSync` via cooperative launch) replace launches
- Warp specialization: GEMV warps, attention warps, norm/residual warps
- Persistent LDS state (input vector stays in LDS across phases)
- Software pipelining: prefetch next layer's weights during current layer
- Requires adding `hippoCooperativeLaunch` and `hippoGridSync` to hippo

### Nim macro kernel fusion DSL
- Define decode pipeline as compile-time dataflow graph
- Macro auto-fuses adjacent ops (e.g., rmsnorm + GEMV keeps intermediate in LDS)
- Macro assigns warps to roles based on CU count and LDS budget
- Type-safe kernel composition: `GpuTensor[Q2K, 2048, 256]` carries quant format
  and dimensions at compile time
- Model params become compile-time constants (no runtime conditionals)
- GPU target becomes compile-time constant (WarpSize, CU count, LDS size)

### Incremental path
1. Auto-fuse rmsnorm + GEMV, validate against hand-written kernel
2. Add grid sync + cooperative launch to hippo
3. Expand macro to handle a full transformer layer
4. Generate entire decode mega-kernel from DSL

## Theoretical ceiling

TinyLlama Q2_K pure weight bandwidth: ~400MB at 960 GB/s = ~2400 tok/s.
Actual ceiling is lower (attention reads KV cache, irreducible compute) but
shows the gap between current 371 tok/s and hardware limits.

## Why Nim

- Compile-time AST manipulation with full Turing-complete logic
- Can write a scheduler that assigns CU workgroups at compile time
- Type system enforces quant format compatibility at compile time
- Result: an ML compiler that fits in a Nim macro library, not a massive
  infrastructure project like XLA or TVM
