# v2.2 — Template backend with compile-time specialization

The fun one. Build a new backend that generates specialized kernels from
compile-time model and machine configs. Not a grand macro DSL — just Nim's
natural `const`, `when`, `static`, and `template` features used to cut all
the runtime overhead out of the hot path.

See docs/wmma-experiment-and-specialized-backend.md for background analysis
on why the naive backend's performance ceiling is low (~10% of bandwidth)
and why specialization is the path forward.

## Philosophy

- Each step is independently useful and testable
- Validate against naive backend output at every step
- Compile-time specialization should make the code simpler, not more complex
- Target "our hardware running our models" — not general purpose

## Tasks

### Step 1: Compile-time model and machine configs

Define model dimensions and hardware specs as compile-time constants.
No new backend yet — just the config infrastructure.

```nim
# -d:HiddenDim=2048 -d:FFNDim=8192 -d:NHeads=32 ...
const HiddenDim {.intdefine.} = 2048
const FFNDim {.intdefine.} = 8192
const NHeads {.intdefine.} = 32
const NKVHeads {.intdefine.} = 8
const HeadDim {.intdefine.} = 64
const NLayers {.intdefine.} = 16
```

```nim
# machine_gfx1151.nim / machine_gfx1100.nim
const CUCount* = 16      # or 96
const LDSSize* = 65536
const MemBandwidthGBs* = 250  # or 960
```

Measure whether the naive backend generates better code when these are
`const` vs runtime values. This alone tells us if the approach is worth
pursuing.

### Step 2: Template backend skeleton

New file: `backends/template.nim`

- Starts by delegating everything to naive backend kernels
- Switched via `-d:backendTemplate`
- Same forward pass structure, just a new dispatch point
- Verify: produces identical output to naive on Llama 3.2 1B

### Step 3: One specialized kernel (Q4K GEMV)

Write a Q4K GEMV that uses compile-time constants for loop bounds and
buffer sizes. Same algorithm as naive, just with `const` dimensions.

Compare:
- Code size (does the compiler actually unroll/optimize differently?)
- Performance (any measurable improvement from literal loop bounds?)
- Readability (is it cleaner or messier?)

This is the proof-of-concept that tells us whether to keep going.

### Step 4: Fuse obvious pairs

Pick operations that always run back-to-back where the intermediate is small:
- RMSnorm + GEMV (eliminate 8KB intermediate write/read)
- GEMV + residual add (fold into epilogue)

Each fusion is one kernel, tested against naive output. Not a framework —
just hand-written fused kernels parameterized by compile-time constants.

### Step 5: Shared-memory x vector across GEMV launches

All GEMV projections in a layer read the same x vector. Load it into shared
memory once, reuse across Q/K/V/O/gate/up/down projections.

Options (increasing ambition):
- Multi-warp blocks where warps share x via LDS
- Persistent kernel that keeps x in LDS across barriers
- Full layer kernel with grid sync

Start with the simplest option that shows improvement.

### Step 6: Machine-aware tuning

Use machine config to set block sizes, warp counts, shared memory budget.
A kernel for gfx1151 (16 CUs, 250 GB/s LPDDR5X) should look different from
one for gfx1100 (96 CUs, 960 GB/s GDDR6X).

Not an autotuner — just `when` branches keyed off compile-time hardware
constants.

## Hardware targets

- gfx1151 (Strix Halo, azem): 16 CUs, LPDDR5X ~250 GB/s, unified memory
- gfx1100 (7900 XTX): 96 CUs, GDDR6X 960 GB/s, discrete VRAM

## Performance targets

Conservative — each step might help a little or a lot. Measure, don't guess.

| Step | What we learn |
|------|---------------|
| Step 1 | Does const-ifying dimensions change codegen at all? |
| Step 3 | Is specialized GEMV measurably faster than naive? |
| Step 4 | How much does eliminating intermediates save? |
| Step 5 | Does x-caching help on LPDDR5X? (prior experiment says maybe not for block GEMV, but persistent kernel is different) |
| Step 6 | Does machine-aware tuning matter, or is one config good enough? |

Overall target: **2-3x improvement** over naive (70-100 tok/s on Strix Halo)
would be a strong result. Anything beyond that is gravy.

## Success criteria

- Template backend produces identical output to naive for Llama 3.2 1B
- At least one step shows measurable performance improvement
- The code is simpler to read than the naive backend, not more complex
